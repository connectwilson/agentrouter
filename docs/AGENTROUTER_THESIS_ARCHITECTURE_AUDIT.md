# AgentRouter 命题与架构审计

审计日期：2026-07-21

## 结论

AgentRouter 不是天然伪命题，但当前产品仍处于“已实现可信付费调用骨架、尚未证明智能路由网络”的阶段。

当前架构已经明显超过 API 目录：它具备结构化 capability request、候选排序、预算检查、付费调用、结果 envelope、确定性校验、证据哈希、消费者反馈和信任分更新。但它尚未完成这个命题最关键的闭环：同一能力的独立供应商竞争、一次请求内自动 fallback、跨供应商语义标准化、以及足以支持质量排序的大规模真实调用数据。

因此，合理的产品定义不是“聚合所有 API”，而是：

> 在一个高价值数据垂直领域，为 Agent 提供按任务动态采购、质量排序、失败回退、标准化结果和可审计来源的执行层。

## 为什么非 AI 时代没有统一所有 API

非 AI 时代并非没有聚合器，而是聚合器的价值通常停留在目录、接入、统一认证、计费或工作流封装。

根本原因：

1. API 选择主要发生在开发阶段，而不是每次请求的运行时。
2. 高调用量业务更重视直接 SLA、稳定性和去除中间层。
3. 同名 API 的数据语义、覆盖范围、授权与错误口径并不一致。
4. 优质供应商不愿完全商品化，也有动力绕过市场平台。
5. 真正成功的聚合器往往承担了更高层工作，例如 Zapier 的 trigger/action、OAuth 和工作流维护，而不只是转发 HTTP。

AI 改变的是消费方式：Agent 会遇到大量低频、临时、跨服务任务，能力选择从 build time 部分转向 runtime。这为路由层创造了新的必要条件，但没有自动创造商业壁垒。

## 当前架构核对

### 已经合理实现

1. **结构化能力协议**：主 Agent 把任务解析为 capability + params，避免把自然语言解析完全塞给 Router。
2. **多维候选排序**：评分考虑 capability、资产、trust、消费者反馈、失败率、health、provenance、freshness 和 price。
3. **支付边界**：Agent 不直接选择收款地址与金额；预算与支付挑战位于调用边界。
4. **结果契约**：`agent_data_envelope_v1` 为 status、data、metadata、limitations 提供稳定位置。
5. **调用后验证**：存在 schema、freshness、coverage、空结果和异常数据检查。
6. **证据链**：绑定 manifest、input、output、verification 与 payment hash；可选 Arc 锚定。
7. **反馈回路**：消费者反馈能改变后续 trust score 和路由顺序。
8. **健康隔离**：熔断服务会从候选排序中排除。
9. **供应商注册门槛**：发布前必须能真实调用并通过 envelope 验证。

### 关键缺口

1. **没有通用自动 fallback**：结构化请求只调用排名第一的服务。失败或低质量时返回 retry plan，但不会自动调用第二名。token resolver 有局部重试，不代表通用能力 fallback。
2. **标准化只到 envelope，不到领域语义**：不同供应商的数据仍原样放进 `data`；无法保证 liquidation、netflow 等字段和口径可以互换。
3. **确定性验证主要验证结构与 sanity，不验证事实正确性**：hash 能证明“返回内容未被改动”，不能证明供应商数据是真的。
4. **trust 冷启动偏乐观**：通过一次注册验证的服务基础分为 0.7；少量成功调用可接近 0.99，但消费者反馈样本很少。
5. **能力 taxonomy 仍带较强手工规则**：核心目录只有若干显式金融能力，动态能力依赖文本、标签与 sample shape。
6. **一次调用只能选一家，尚不能做多源交叉验证或 consensus**。
7. **支付复杂度跑在需求验证之前**：支付与链上证据完成度高于路由质量和需求密度，存在优化错位。

## 验证结果

### 本地工程验证

- 执行 `npm test`：117/117 通过。
- 覆盖支付、注册、结构化路由、反馈更新排序、熔断、证据、MCP、CLI 和 Arc 支付。
- 测试证明基础设施机制可运行，但不能证明真实市场供需或路由效果。

## 是否是伪命题

### 以下版本很可能是伪命题

- 收录大量 API/MCP。
- 用描述匹配一个工具。
- 提供统一 Key 或 x402 支付。
- 返回上游原始 JSON。

这一层会受到 MCP Registry、模型厂商的 tool search、Zapier、Apify 和 API 提供商自建 MCP 的挤压。

### 以下版本有成立机会

- 只服务一个有多个非同质数据商的高价值领域。
- 用户愿意为一次正确结果而不是 API 调用本身付费。
- Router 能通过真实评测知道不同任务该信谁。
- 失败时在同一次请求内自动切换，并且避免重复扣费或明确累计预算。
- 输出统一领域对象，同时保留 provider 原始证据。
- 能进行多源交叉验证并标注分歧。
- 对数据授权、时效和商用权限给出机器可读 provenance。

## 建议的产品边界

继续聚焦加密市场/链上数据，而不是“全网 API”。这个垂直领域具备：

- 多供应商与数据差异；
- 时间敏感；
- 单次高价值；
- Agent 临时组合需求；
- 错误结果代价明显；
- 可用公开链上数据做部分交叉验证。

建议承诺：

> AgentRouter 在预算内返回一个标准化、带来源、带新鲜度与质量说明的市场数据结果；若首选供应商失败，会自动换源，并记录每次尝试与费用。

不要承诺：

> AgentRouter 聚合所有 API，并总能选到最好的一家。

## 优先级

### P0：验证命题

1. 选择一个能力，例如 `perp_liquidation_max_pain`。
2. 接入至少 3 个真正独立供应商，不是同一供应商的多个 endpoint。
3. 建立 50～100 个带预期结果特征的离线/定时评测任务。
4. 比较 Router 与固定首选供应商在成功率、新鲜度、覆盖率、成本和延迟上的差异。
5. 获得至少 10 个外部 Agent 开发者、每人 20 次以上真实调用。

### P1：补齐架构核心

1. 把 retry plan 变成预算感知的自动 fallback executor。
2. 为首个垂直能力定义 canonical result schema 和 provider adapter。
3. 区分 integrity、structural quality、factual accuracy 三种信任。
4. 给 trust score 增加样本量置信区间和冷启动惩罚。
5. 加入 shadow evaluation：非付费或低成本抽样比较未选中的候选。

### P2：之后再强化

- 多源 consensus。
- 学习排序模型。
- 更广泛的支付网络。
- 扩展到第二个数据垂直领域。

## Go / No-Go 判据

在单一 capability、3 个独立供应商、至少 500 次外部真实请求后：

- Router 相比固定供应商，端到端成功率提升至少 15%；
- 在相同质量阈值下，平均成本不高于固定方案 20%；
- 95% 请求能够返回 canonical schema；
- 自动 fallback 在首选失败时恢复至少 60% 请求；
- 至少 30% 外部开发者在四周内重复调用；
- 至少 20% 调用愿意实际付费。

若达不到这些标准，应把产品收缩为某个数据产品/API，而不是继续建设通用路由网络。
